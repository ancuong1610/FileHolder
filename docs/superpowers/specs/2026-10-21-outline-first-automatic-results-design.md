# Outline-first structure and automatic comparison results

Status: owner-approved for implementation: outline-first structure, documentation
discipline, automatic uncertainty results and human-friendly reporting. Source
strikethrough is explicitly deferred by the owner and is not part of this
implementation. Table-quality diagnosis still needs a representative failing
sample; do not claim that an unobserved extraction defect has been repaired.
No runtime change is implemented merely by this document.

## Outcome and approved decisions

The user uploads/selects two PDFs, the comparison runs automatically, and one
complete result explains supported changes, uncertain differences and extraction
limitations. There is no required human approval step or task queue to complete
the comparison. Uncertainty must not be hidden or relabelled as certainty.

Three approved changes:

1. Prefer usable PDF outline/bookmark evidence obtained locally before DI. When
   absent, invalid or partial, retain the current structure-reconstruction path.
2. Coding agents assess documentation impact before every commit and update
   affected docs with the code, rather than leaving README/design guidance stale.
3. Remove the human-review workflow vocabulary/path from new routing and user
   presentation while retaining evidence-backed uncertainty and safe failure.

## Current implementation and boundaries

- Stage 1 reads configured PDF paths and extracts/reuses DI chunks. It does not
  currently collect PDF outlines. PyMuPDF is already a project dependency.
- Stage 5 builds provisional anchors and additive TOC/section/furniture evidence.
  Neither is authoritative hierarchy. Raw roles/text/IDs/eligibility are retained.
- `HUMAN_REVIEW` currently marks evidence; it does not pause Stage 11 or ask a
  person to authorize continuation. The change is to routing semantics and a
  complete automatic result experience, not removal of an existing blocking UI.
- Stage 14 retains uncertain changes and evidence under legacy review fields.
  Stage 15's HTML and accepted-change index currently omit uncertain changes.
  Reader tools include unresolved records but use review terminology.
- Source PDFs remain external through `CRR_OLD_PDF`/`CRR_NEW_PDF`. Input relocation,
  DI replacement, Docling production integration, new dependencies, deployment
  and the Stage 10 all-pairs performance fix are out of scope.
- Keep 15 pipeline stages, existing CLI entry points and the one-way phase
  dependency direction. Do not add a new model/provider or mandatory model call.

## 1. PDF outline prepass and reconciliation

### Acquisition

At the beginning of the PDF-based Stage 1 path, use PyMuPDF's native outline API
before any DI request. Base64 is only transport encoding; it does not strip PDF
structure. Do not claim that adding a TOC to our metadata makes DI consume it.

Save versioned `old_pdf_outline.json` / `new_pdf_outline.json` sidecars under
`output/`. Each records the source PDF SHA-256, physical page count, acquisition
status, validated entries and diagnostics. Entries retain source order, level,
title and destination evidence; they do not invent source-element IDs.

Distinguish embedded bookmarks from a visible contents page and from outlines
generated by a viewer. An empty native outline is a normal fallback condition.
Do not implement a second OCR/printed-TOC detector in this prepass.

### Identity and validation

- Bind outline evidence to the PDF bytes, not just its filename. Carry matching
  extraction-source identity through the internal model so Stage 5 can reject
  a stale/unrelated sidecar without requiring the original PDF to remain present.
- Validate local destinations and physical page bounds. Preserve PDF page labels
  separately; a printed page number is not a physical page index.
- Invalid/out-of-document/external destinations are diagnostics, not fabricated
  headings. Partial outlines contribute only supported entries.
- An outline-read failure does not by itself abort otherwise valid DI processing.
  A PDF/extraction failure still follows existing actionable failure behavior.
- Legacy cache/raw inputs with no verifiable outline identity use current
  reconstruction. Never trust a sidecar merely because it exists in the workspace.

### Stage 5 use

Read verified prepass evidence and reconcile entries against the extracted
elements using destination/location and title/label evidence. Keep provenance for
embedded outline, printed TOC and inferred body structure separate. A bookmark
title is not itself an authoritative DI element or proof of semantic hierarchy.

Use supported outline links as preferred structural evidence and as anchor/context
support. Do not force an ambiguous match, cross contradictory labels, promote
derived furniture, or suppress unmatched body content. Existing inference fills
uncovered regions; conflicting evidence remains explicitly uncertain. No valid
outline must reproduce the existing fallback behavior.

The prepass does not itself introduce hard section partitions in Stage 10. Using
structure for bounded table-candidate retrieval is a separate performance change
with its own recall tests.

## 2. Automatic results without mandatory review

### New execution/presentation semantics

Replace the new-run `HUMAN_REVIEW` routing branch with an uncertainty-result
route, named `UNCERTAIN_RESULT`. Existing optional evaluator routes run according
to `CRR_RUN_LLM`; disabled/failed evaluation preserves uncertainty and does not
request human action. Keep evaluator advice subordinate to deterministic rules.

Results distinguish:

- **Supported change:** the current engine rules support this difference, not a
  claim of legal/human verification.
- **Uncertain difference:** a candidate or structural/table ambiguity remains,
  with the reason and available source/change references.
- **Non-semantic event:** supported layout/artifact/structural-only handling,
  retaining existing suppression guards and audit evidence.

Do not introduce an approval button, resume-after-review state or mandatory
queue. Do not invent calibrated confidence percentages. Severe extraction or
contract failures must not become a successful empty comparison. Incomplete
quality evidence must be visible in the result's limitations.

### Canonical data and saved-workspace compatibility

Preserve existing machine-readable artifact names and the established reader
contract in this slice. Legacy fields such as `resolution.status=review`,
`needs_review`, `review_queue` and typed `kind=review` references remain readable
as compatibility terminology for uncertainty, not instructions to an operator.
Do not rewrite an existing workspace to migrate its labels.

Add an explicit normalized `result_state` to new resolution records, using
`supported`, `uncertain`, or `non_semantic` as appropriate. Readers derive this
state from legacy resolution when it is absent. Preserve the detailed legacy
statuses for compatibility/audit rather than changing `review` to `accepted`.
Both `HUMAN_REVIEW` in old artifacts and new `UNCERTAIN_RESULT` map to uncertain
results. Internal producers must stop emitting new human-action routes.

Use one canonical set of uncertainty records. Do not concatenate duplicate old
and new queues or count the same evidence twice. Existing filter/typed-reference
forms continue to work; human-facing labels and agent explanations use the new
semantics. No general compatibility framework or old namespace shim is added.

### Complete reports and reader/agent behavior

- HTML/PDF results include supported changes and uncertain differences in clearly
  separated sections with counts and available old/new values, pages and evidence.
  Evidence-only cases without a trustworthy pair stay visible without inventing
  old/new correspondence.
- The canonical result, not an accepted-only projection, determines completeness.
  `phase2_change_index.json` retains its accepted-only corpus contract; it must
  not become the sole source for the complete report.
- The legacy CSV may remain an optional uncertainty export for consumers. It is
  not required user work and must not be the only place uncertain cases appear.
- A no-change message cannot imply equality while uncertain cases or severe
  extraction limitations exist. Report these conditions explicitly.
- Reader summaries/search/details and the Q&A agent preserve bounded retrieval,
  evidence citations, pagination, job isolation and existing saved-result support.
  They do not ask for approval to finish comparison, omit uncertainty by default,
  or describe uncertain findings as accepted truth.

## 4. Human-friendly Stage 15 report (scope extension)

Audience: a person comparing two documents, not an engine developer. The primary
report should answer what changed, where, and how well it is supported, without
requiring knowledge of stage numbers, route IDs or JSON schemas.

- Begin with recognizable old/new document identities, a plain-language summary,
  supported/uncertain counts and relevant extraction limitations. Do not generate
  an LLM summary that claims more certainty than canonical records support.
- Group results under readable section/outline titles where supported, otherwise
  source pages or clearly named unassigned groups. Inferred labels remain hints,
  not verified hierarchy.
- Present each difference as a readable before/after comparison with local context
  and source page references. Uncertain differences remain in the primary report
  with a short explanation, not only a separate machine-oriented export.
- Render table changes as recognizable row/column/cell comparisons rather than
  a long undifferentiated list of IDs. Preserve exact numeric values, units and
  source identity when row alignment is uncertain; do not fabricate a neat pairing.
- Put technical IDs, matching scores, provenance and route details behind an
  optional details section in HTML or in a clearly separated technical appendix
  in PDF. Keep the evidence accessible rather than deleting it.
- Explain the visual legend in ordinary language and with text labels as well as
  colors. Distinguish source strikethrough from report-generated deletion marks.
- Prefer the existing self-contained HTML/PDF outputs over introducing a new app
  or remote fonts/assets. This extension does not choose new palette/typography
  or approve a particular visual mockup. Human visual feedback is the acceptance
  gate; do not start automatic browser/screenshot review loops.

## 5. Table-quality and source-strikethrough investigation (scope extension)

**Current execution boundary:** retain the investigation below for future work.
Do not implement source-strikethrough detection or change its matching behavior
in the present slice. Table diagnostics must not become speculative extraction
or matching changes without a reproducible input.

### Separate the failure layers

"The table was scanned badly" can mean missing/wrong DI cells, damaged internal
representation, bad logical-table grouping, wrong OLD/NEW or row alignment, or
an unreadable/incorrect rendering. Compare the source page with raw DI, Stage 3,
Stage 5, Stage 10, canonical and Stage 15 evidence before selecting a repair.
The earlier Stage 10 performance finding does not establish any one of these
quality causes. No private failing table page/artifacts have been supplied yet.

### Source strikethrough is not the report's deletion notation

The owner supplied an illustrative screenshot showing a line across a word.
Working assumption: the mark is in the source PDF; confirm on an actual PDF page.
An image alone cannot establish whether it is a PDF annotation, a vector drawing
over live text, rasterized pixels, or another kind of visual mark.

Code inspection confirms that the current internal paragraph model does not
retain source strikethrough evidence, and the exact-match key is only
`(element_type, comparison_text)`. Current rendering strike tags represent
comparison deletions, not native source formatting extraction.

A local synthetic probe created plain text, a native PDF `StrikeOut` annotation
and a vector line over the same text. PyMuPDF returned identical plain text in
all three; annotations/drawings differed, while the inspected text-span flags
did not distinguish the cases. Feeding those equal strings through actual Stage
3–6 functions using explicitly synthetic text-only DI carriers produced one
exact match and no source-style fields. No DI request was made. This reproduces
a source-format blind spot, not the owner's particular PDF/OCR behavior.

### Proposed repair boundary, after representative evidence

- Acquire local source-format evidence separately from the plain-text channel.
  Native strikeout annotations, vector-line geometry and rasterized marks require
  different evidence; do not pretend one text flag detects them all.
- Bind source-format evidence to the correct PDF/page/text span and preserve
  provenance and raw strings through the internal model.
- Detect a changed source mark even when comparison text is identical. Do not
  silently discard that case as unchanged before downstream reporting can see it.
- Do not automatically delete or suppress source-struck text. A source mark is
  evidence to represent and compare, not blanket permission to erase content or
  declare a legal deletion.
- Protect against table borders, underlines and unrelated crossing lines being
  labelled as proven strikethrough. Ambiguous vector evidence stays uncertain.
- If scanned/rasterized markup cannot be established by the available extractor,
  name the limitation rather than inventing formatting metadata or forcing a
  new model/service into the pipeline.
- Regression coverage must distinguish same-text/different-mark, identical marks
  on both sides, partial-word marks, native annotations, vector lines and table
  border/underline negatives. A private-case success claim requires reproduction
  on a permitted original/anonymized PDF example.

## Acceptance and verification boundaries

- Synthetic PDF tests: complete/absent/partial/malformed outline; invalid/external
  destination; page labels versus physical pages; duplicate/conflicting titles;
  stale source hash; legacy cache without outline evidence; extraction succeeds
  when only outline acquisition fails.
- Stage 5 regressions: existing TOC/furniture cases remain valid; outline links
  never promote furniture or invent hierarchy; raw text/IDs/conservation remain.
- Routing/canonical tests: no new `HUMAN_REVIEW`; old and new uncertainty routes
  stay uncertain; no forced acceptance/suppression; optional evaluator failure or
  disablement never requires approval or erases a difference.
- Report tests: uncertainty visible in the primary report, distinct counts,
  numeric old/new preservation, no false no-differences message, no fabricated
  pairing for unresolved tables, no semantic duplication from evidence queues.
- Reader/API/MCP/agent tests: old workspace readable without writes, consistent
  uncertainty explanation, existing typed references/filters, bounded responses
  and job isolation unchanged. Existing transport mock remains applicable.
- Relevant focused tests after each coherent change; complete unittest suite,
  offline demo/report assertions and real-transport mock at the final boundary.
  Inspect the actual diff and doc links/examples before any authorized commit.
- One independent final review is warranted for the cross-consumer contract and
  uncertainty boundary. If unavailable, record the blocker and self-review
  limitation explicitly rather than claiming independent approval.
- No live DI/LLM calls or private-document upload for automated verification.
  Synthetic acceptance does not prove company-PDF accuracy or solve the 600-table
  runtime problem. Source PDFs remain in their existing external locations.
